# rag-eval-bench

[![ci](https://github.com/socrabs151/rag-eval-bench/actions/workflows/ci.yml/badge.svg)](https://github.com/socrabs151/rag-eval-bench/actions/workflows/ci.yml)
[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![python](https://img.shields.io/badge/python-3.11%2B-blue.svg)](pyproject.toml)

Воспроизводимый стенд для Retrieval-Augmented Generation: аблации retrieval, качество ответов
и готовый интерфейс для прогонов, evals и датасетов.

**Статус: рабочий, до стадии judge.** BM25, dense и hybrid retrieval вместе с cross-encoder
реранкингом запускаются на встроенном демо-корпусе и на SciFact; экстрактивный baseline
и генерация через Ollama подключены; метрики retrieval, реранкинг и хранилище прогонов покрыты
тестами и CI. LLM-as-a-judge и статистические тесты — следующие этапы (см. [Планы](#планы)).

## Зачем

Почти каждый RAG-проект заново собирает одни и те же экраны: таблицу прогонов, кривые метрик,
сравнение двух оценок, просмотр датасета. Эта обвязка — не исследование. Здесь эксперимент
и есть продукт, а [frontedge](https://github.com/socrabs151/frontedge-ml) используется как слой
интерфейса: FastAPI-роутер с прогонами, деталями прогона, сравнением, eval diff и датасетами на
трёх небольших провайдерах.

Интерфейс — зависимость, а не предмет работы. Предмет: какая конфигурация retrieval лучше,
сколько это стоит и можно ли доверять оценке.

## Что уже работает

- **BM25** по перекрывающимся символьным чанкам, чистый Python.
- **Dense retrieval** через `sentence-transformers` и **hybrid RRF** по двум ранжированиям.
- **Cross-encoder реранкинг** найденных кандидатов (`ms-marco-mini` или `bge-base`); латентность
  retrieval и реранкинга записывается отдельно.
- **Экстрактивный baseline-генератор**: возвращает предложение из контекста, ближайшее к
  вопросу, поэтому конвейер детерминирован и работает офлайн.
- **Генератор Ollama**: локальные модели через chat API, включается флагом
  `--generator ollama`.
- **Метрики**: Recall@k, MRR, token F1, exact match; метрики ответов считаются только там,
  где в датасете есть эталонные ответы.
- **Раннер экспериментов**: оценивает каждый вопрос, агрегирует метрики и пишет один JSON-прогон
  в `artifacts/runs/`.
- **Загрузка датасетов**: `fetch-data` скачивает публичный бенчмарк, проверяет каждый файл по
  закреплённому SHA-256 и конвертирует его в формат хранилища.
- **Провайдеры frontedge**:
  - runs: фильтрация, сортировка и пагинация на стороне сервера, примеры по прогону;
  - evals: попарное сравнение двух прогонов;
  - datasets: версии, datasheet и provenance.

## Быстрый старт

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"

# демо-корпус, без сети
rag-eval-bench run --retriever bm25 --k 5

# публичный бенчмарк
rag-eval-bench fetch-data --dataset scifact
rag-eval-bench run --data-dir datasets/scifact --retriever bm25 --k 5

# dense и реранкинг требуют опциональный extra
pip install -e ".[retrieval]"
rag-eval-bench run --data-dir datasets/scifact --retriever hybrid --k 5 
    --reranker ms-marco-mini --candidates 20

# интерфейс
rag-eval-bench serve
```

Интерфейс: <http://127.0.0.1:8000/frontedge>. API — по пути `/frontedge/api`.
`artifacts/` в git не попадает; демо-прогоны в `data/runs/` закоммичены.

Есть Docker: `docker build -t rag-eval-bench .`, затем
`docker run --rm -p 8000:8000 rag-eval-bench`.

## Данные

| id | источник | размер | эталонные ответы | назначение |
|----|----------|--------|------------------|------------|
| `scifact` | [SciFact (BEIR)](https://huggingface.co/datasets/mteb/scifact) | 5 183 аннотации, 300 размеченных утверждений | нет | качество retrieval |
| `ml-glossary` (встроенный) | этот репозиторий | 12 заметок, 8 вопросов | да | smoke-тесты, разработка UI |

`fetch-data` закрепляет коммит источника и SHA-256 каждого файла, проверяет их до конвертации
и пишет `manifest.json` рядом с данными. Изменённый на стороне источника файл ломает загрузку,
а не тихо меняет цифры. В SciFact есть разметка релевантности, но нет эталонных ответов,
поэтому F1 и faithfulness для него не считаются; качество ответов — задача этапа judge.

Лицензия: SciFact распространяется по CC BY-SA 4.0 (Wadden и др., 2020; дистрибуция BEIR).
Данные скачиваются при запуске и в репозиторий не попадают.

### Аблация

`scripts/run_ablation.py` прогоняет четыре конфигурации через публичный раннер и пишет
[`reports/scifact-ablation.md`](reports/scifact-ablation.md) вместе с JSON-копией. Таблица ниже —
этот отчёт целиком, перегенерированный, а не набранный руками.

| Retrieval | Recall@5 | MRR@10 | retrieval, мс | rerank, мс | всего p50, мс | всего p95, мс |
|---|---:|---:|---:|---:|---:|---:|
| BM25 | 0.650 | 0.545 | 143 | — | 138 | 194 |
| Dense (multilingual e5-small) | 0.623 | 0.534 | 18 | — | 18 | 22 |
| Hybrid (RRF) | 0.703 | 0.599 | 232 | — | 218 | 384 |
| Hybrid + cross-encoder | 0.747 | 0.625 | 245 | 257 | 485 | 680 |

Условия: 300 размеченных утверждений, `k=5`, 20 кандидатов на реранкинг, чанки 400 символов
с перекрытием 50, экстрактивный генератор. Латентность — среднее на запрос без времени
построения индекса; итоги — p50/p95 по примерам; машина без GPU, поэтому абсолютные значения
на другом железе будут другими.

Что видно по цифрам: hybrid RRF обходит оба первых этапа, а cross-encoder добавляет 4,4 пункта
recall при примерно двукратной латентности. Небольшая мультиязычная dense-модель на английских
биомедицинских аннотациях оказывается чуть хуже BM25 — ожидаемый результат для этого корпуса
и повод попробовать модель крупнее или дообученную под домен.

Полное воспроизведение на CPU занимает около 30 минут:

```powershell
python scripts/run_ablation.py --data-dir datasets/scifact --out reports/scifact-ablation.md
```

Это локальные ориентиры, а не строчка в лидерборде: BEIR публикует nDCG@10 по полным
документам, а чанкинг и латентность здесь зависят от машины.

## Как устроена оценка

Для каждого вопроса раннер достаёт `k` чанков, генерирует ответ и фиксирует:

- `recall_at_5` — попал ли эталонный документ в топ-5;
- `mrr_at_10` — обратный ранг первого эталонного документа;
- `f1` — пересечение токенов ответа и эталона, если эталон есть;
- `retrieval_ms` и `rerank_ms` — средняя латентность этапов, когда включён реранкер;
- `latency_ms` — retrieval, реранкинг и генерация вместе.

Агрегаты — средние по вопросам; ряды — накопительные средние по шагам, поэтому в деталях
прогона есть кривая. Каждый пример хранит вопрос, оба ответа, id найденных документов и свой
балл — именно это построчно сравнивает экран eval diff.

`faithfulness` зарезервирован под этап judge: демо-данные хранят значение прошлой разметки,
раннер пишет `0.0`, пока судья не подключён.


Скрипт работает с `socrabs151/frontedge-ml` и использует `GITHUB_TOKEN` или сохранённые
git-credentials. После отправки впишите URL issue в колонку `Upstream` журнала.

## Планы

1. LLM-as-a-judge с вручную размеченной подвыборкой и калибровкой по Cohen's kappa.
2. Bootstrap-доверительные интервалы и парные тесты по примерам.
3. Токенный чанкинг и более крупный dense-энкодер, перемеренные той же аблацией.
4. Матрица генераторов (локальные 1.5B–7B и одна хостед-модель) со стоимостью токенов на
   1 000 запросов.
5. Приём реального корпуса документов и версионирование датасетов.

## Заметки

- `frontedge` закреплён на `0.5.x` (публичная бета). Держите провайдеры за тонкими адаптерами
  репозитория, чтобы изменения библиотеки оставались локальными.
- Python 3.11+; демо не требует GPU и сети.
- Для локальных моделей на Windows/AMD Ollama опционален. Экстрактивный baseline работает всегда.
- Большой кэш моделей не место на маленьком системном диске: направьте `HF_HOME` и
  `OLLAMA_MODELS` на диск с данными.
