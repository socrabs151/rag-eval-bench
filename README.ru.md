# rag-eval-bench

Воспроизводимый стенд для Retrieval-Augmented Generation: абляции retrieval, качество ответов и
готовая интерфейсная часть для запусков, оценок и датасетов.

**Статус: скелет.** Проект работает на встроенных демо-данных и делает настоящие запуски
экспериментов с BM25 и детерминированным извлекающим генератором. Плотный retrieval, реранкеры,
локальная генерация через LLM и калибровка judge подключены как точки расширения, а не как
готовые функции.

## Зачем

Почти каждый RAG-проект заново собирает одни и те же экраны: таблицу запусков, кривые метрик,
сравнение двух оценок, просмотр датасета. Эта обвязка — не исследование. Здесь продуктом остаётся
эксперимент, а [frontedge](https://github.com/socrabs151/frontedge-ml) используется как слой
интерфейса: FastAPI-роутер с запусками, деталями запуска, сравнением, eval diff и датасетами,
который кормится тремя небольшими провайдерами.

Интерфейс — зависимость, а не предмет работы. Предмет: какая конфигурация retrieval лучше,
сколько она стоит и можно ли доверять оценке.

## Что уже работает

- **BM25** по перекрывающимся символьным чанкам, чистый Python.
- **Извлекающий базовый генератор**: возвращает предложение контекста, ближайшее к вопросу,
  поэтому пайплайн детерминирован и работает офлайн.
- **Генератор Ollama**: локальные модели через chat API, включается флагом
  `--generator ollama`.
- **Метрики**: Recall@k, MRR, token F1, exact match.
- **Запуск эксперимента**: оценивает все вопросы, агрегирует метрики и пишет один JSON-запуск
  в `artifacts/runs/`.
- **Провайдеры frontedge**:
  - runs: фильтрация, сортировка и пагинация на стороне провайдера, примеры по запуску;
  - evals: попримерное сравнение двух запусков;
  - datasets: версии, datasheet и provenance.
- **Демо-данные**: 12 заметок глоссария, 8 вопросов, 3 завершённых запуска с попримерными
  доказательствами.

## Структура

```text
app.py                     точка входа для uvicorn
frontedge.toml             колонки, метрики, baseline, размер страницы
data/                      демо-корпус, вопросы, запуски, evals, датасеты
scripts/build_demo_data.py пересобирает data/ из одного источника правды
src/rag_eval_bench/
  app.py                   FastAPI + frontedge.mount
  providers/               адаптеры runs / evals / datasets
  retrieval/               bm25, dense, hybrid (RRF)
  generation/              извлекающий baseline, клиент Ollama
  evaluation/              метрики и запуск эксперимента
  storage.py               JSON-хранилище корпуса и запусков
tests/                     метрики, чанкинг, retrieval, провайдеры, API
```

## Быстрый старт

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
frontedge check frontedge.toml
uvicorn app:app --reload
```

Откройте <http://127.0.0.1:8000/frontedge>. API живёт под `/frontedge/api`.

Запустить эксперимент (перезапустите сервер, чтобы увидеть его в интерфейсе):

```powershell
rag-eval-bench run --retriever bm25 --k 5
```

Команда пишет `artifacts/runs/<run-id>.json`. Каталог `artifacts/` в `.gitignore`; демо-запуски
в `data/runs/` закоммичены.

## Данные

`data/` генерируется. Правьте `scripts/build_demo_data.py` и запускайте его, а не JSON руками:

```powershell
python scripts/build_demo_data.py
```

Корпус англоязычный и написан для этого репозитория. Это дымовой фикстур, а не бенчмарк: восьми
вопросов слишком мало для сравнительных выводов. Перед выводами замените корпус на реальный.

## Как устроена оценка

Для каждого вопроса запуск достаёт `k` чанков, генерирует ответ и записывает:

- `recall_at_5`: попал ли золотой документ в топ-5;
- `mrr_at_10`: обратный ранг первого золотого документа;
- `f1`: пересечение токенов ответа и эталона;
- `latency_ms`: время retrieval и генерации.

Агрегаты — средние по вопросам; ряды — накопленные средние по шагам, поэтому у деталей запуска
есть кривая. Каждый пример хранит вопрос, оба ответа, id найденных документов и свою оценку —
именно это экран eval diff сравнивает построчно.

`faithfulness` зарезервирована под judge: в демо-данных стоит значение прошлого прохода
аннотации, а runner пишет `0.0`, пока judge не подключён.

## Обратная связь по frontedge

Находки по зависимости ведутся в
[`docs/frontedge-feedback.md`](docs/frontedge-feedback.md): у каждой записи есть минимальное
воспроизведение, обходной путь и предложение по изменению. Отправить запись наверх:

```powershell
python scripts/file_frontedge_issue.py --entry F-002 --dry-run
python scripts/file_frontedge_issue.py --entry F-002
```

Скрипт целится в `socrabs151/frontedge-ml` и берёт `GITHUB_TOKEN` или сохранённые учётные данные
git. После отправки впишите URL issue в колонку `Upstream` журнала.

## План

1. Плотный retrieval (`sentence-transformers`) и cross-encoder реранкер в гибридном пути.
2. Матрица генераторов: 1.5B / 3B / 7B через Ollama плюс одна хостинговая модель для точки на
   Pareto.
3. LLM-as-a-judge с подвыборкой ручной разметки и калибровкой по Cohen's kappa.
4. Bootstrap-доверительные интервалы и парные тесты по попримерным оценкам.
5. Загрузка реального корпуса и версионирование датасетов.

## Заметки

- `frontedge` закреплён на `0.5.x` (public beta). Провайдеры держите за тонкими адаптерами этого
  репозитория, чтобы изменения библиотеки оставались локальными.
- Python 3.11+; демо не требует GPU и сети.
- Для локальных моделей на Windows/AMD Ollama опционален. Извлекающий baseline работает всегда.
- Большой кэш моделей не место на маленьком системном диске: направьте `HF_HOME` и
  `OLLAMA_MODELS` на диск с данными.
